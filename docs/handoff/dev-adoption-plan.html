1. 前提と方針

1.1 ブランチ実態(実測済み)

リポジトリ存在ブランチ(実測)HEAD
booking-backenddevelop(+マージ済み feature)d8e3522
booking-frontenddevelop(+マージ済み feature)8596eff

2 つのアプリ リポジトリには master / main は存在しない(booking-deploy には origin/master が残存している点に注意 — workflow の branches フィルタは deploy リポジトリ上では生きている)。したがって dev 適用にあたり、アプリ側の成果物タグは develop(可変ブランチタグ・3 サービス共通で生成される)と develop-<sha>(backend/migration の不変タグ)・sha-<sha>(frontend の不変タグ)のみが実在する前提とする。

1.2 prod を後回しにする理由

  1. アプリ側に prod 用タグ(master / master-<sha>)を生成するブランチが実在しない。
  2. P0: frontend の NEXT_PUBLIC_* がビルド時焼き込みで、prod の API URL が実行時注入できない(アプリ側 Dockerfile 改修が前提)。
  3. prod 固有の課題(TLS 無し+Secure Cookie 強制、SF 鍵マウント等)は dev 適用の前提を阻害しないため分離。

1.3 dev 適用のゴール

  • 検証ゲート(verify-images dev leg / verify-images.sh)が「失敗を失敗として報告する」状態になる。
  • CI の dev leg が実在する develop 系タグで green になる。
  • ローカルから verify-images.sh dev が完走する。
  • 前提修正済みの migration イメージで seed を実行し、ログイン可能な初期ユーザーが存在する。

進捗(2026-09-22): ゴール 1〜4 すべて達成 ✓(負試験 2 経路合格 / CI verify-images dev leg green = PR #5・1m39s / ローカル通し実行成功 / seed 後に実メール受信・ログイン成功)。

5. 受け入れ基準(Acceptance Criteria)

  • 負試験(G-1): verify-images.sh dev の待機ループ中に別端末で docker stop booking-backend-dev(または booking-postgres-dev)→ タイムアウト後に非 0 終了し logs/down が走る。

  • タグ実在(G-5/G-6): CI dev leg が生成する compose env のイメージ参照が :develop であり、pull・起動が成功する。
  • env トリガー(G-7): env/** のみを変更した PR で verify-images.yml が起動する。
  • seed(G-11): Step 5 の前提修正済みイメージで seed が成功し、ログイン可能。
  • uploads 永続化(G-10): docker compose ... up -d --force-recreate backend 後も uploads 配下のファイルが残る。
  • プロジェクト分離(G-12): docker compose -f compose/docker-compose.dev.yml ps のプロジェクト名が booking-dev になり、dev の down -v が他スタック(prod 復活後)を破壊しない。
